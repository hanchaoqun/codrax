# Codrax Trace 简短根因与聚类说明（小白版）

## 1. 这个功能做什么

Codrax 原来会输出一份完整、较长的 Trace 分析。

现在增加了两个可选能力：

1. 从真实 Trace 证据中生成简短、统一的根因；
2. 把多份 Trace 中相同的根因放到同一组。

原来的长答案仍然保留。简短根因只是放在长答案上方的一小段结构化结果。

## 2. 数据从哪里来

根因不是只根据提示词猜出来的。

单个 Trace 使用 `--htrace` 传入真实文件：

```powershell
.\codrax.exe `
  --htrace ".\demo.trace" `
  --request "分析这个 Trace，并且需要简短根因" `
  --lang zh
```

程序会读取 `demo.trace` 的真实内容，再从结构化证据中选择根因。

提示词只负责说明你想要什么输出，不能代替 Trace 文件。

## 3. 什么时候显示简短根因

简短根因是按需显示的。

提示词中明确出现下面这类说法时才会显示：

- `需要简短根因`
- `显示简短根因`
- `输出简短根因`
- `给出简短根因`
- `生成简短根因`

例如：

```text
分析这个 Trace，并且需要简短根因
```

如果提示词只是：

```text
分析这个 Trace 的卡顿原因
```

程序只输出原来的长答案。

如果提示词写了：

```text
不需要简短根因，只输出完整分析
```

程序同样只输出原来的长答案。

## 4. 简短根因长什么样

简短根因位于长答案上方，并且是合法 JSON：

````markdown
## 简短根因

```json
{
  "thread_name": "RenderThread",
  "root_cause": "RenderThread线程CPU调度延迟"
}
```

---

## 完整分析

这里开始是原来的完整长答案……
````

JSON 只有两个主要字段：

| 字段 | 含义 |
|---|---|
| `thread_name` | Trace 证据中的线程名 |
| `root_cause` | 按固定规则生成的简短根因 |

## 5. 根因只能使用哪些形式

程序把底层的技术 Token 统一映射到下面 11 种形式。

| 根因类型 | 输出形式 | 示例 |
|---|---|---|
| IO 阻塞 | `<线程名>线程IO阻塞` | `RenderThread线程IO阻塞` |
| 锁竞争 | `<锁名或资源名>锁竞争` | `ClassLinker classes lock锁竞争` |
| 同步 Binder 阻塞 | `<线程名>线程同步binder` | `UI线程同步binder` |
| 优先级反转 | `<线程名>线程优先级反转` | `Worker线程优先级反转` |
| GC | `GC耗时长` | `GC耗时长` |
| CPU 调度延迟 | `<线程名>线程CPU调度延迟` | `RenderThread线程CPU调度延迟` |
| 阶段高负载 | `<阶段名>阶段高负载` | `DrawFrame阶段高负载` |
| JIT 编译 | `<线程名>线程JIT编译耗时` | `JitThread线程JIT编译耗时` |
| Shader 编译 | `<线程名>线程Shader编译` | `RenderThread线程Shader编译` |
| sleep 阻塞 | `<线程名>线程阻塞` | `UI线程阻塞` |
| 供给不足 | `供给不足` | `供给不足` |

线程名、锁名、资源名和阶段名都优先来自 Trace 的结构化证据。

## 6. 根因怎样被选出来

处理过程可以简单理解为：

```text
读取真实 Trace 文件
        ↓
解析线程状态、调度、Binder、IO、锁和语义阶段
        ↓
生成带证据编号的根因候选
        ↓
按照原有根因榜排名
        ↓
选择排名最高且允许作为主因的候选
        ↓
映射到固定的 11 种简短形式
        ↓
生成 JSON
```

简短根因不是从长答案里截取一句话，也不需要模型再总结一次。

这可以避免简短根因和底层 Trace 证据互相矛盾。

## 7. 为什么不会再影响原来的长答案

旧方案把 `trace_finding` 强制加入模型的最终答案工具格式。

模型如果没有正确填写这个新字段，整个最终答案可能失败，并显示：

```text
无法继续：最终答案生成失败
```

现在改成：

1. 模型继续使用原来的最终答案格式；
2. 原来的长答案先正常完成；
3. 程序再从已经存在的 Trace 结构化证据生成简短根因；
4. 只有用户明确需要时，才把 JSON 放到长答案上方。

因此，没有请求简短根因时，长答案输出保持原样。

## 8. 如果证据不足怎么办

程序不会为了凑格式编造根因。

如果 Trace 没有形成任何可用候选，结构化 Finding 会标记为未确定。

请求简短根因时会输出类似：

```json
{
  "thread_name": "",
  "root_cause": "无法从原始 Trace 的结构化证据中确定根因"
}
```

正常的、可解析且包含相关事件的 Trace 通常会形成候选，并进入前面的 11 类。

## 9. 同一级目录有很多 Trace 怎么办

可以使用批量命令：

```powershell
.\codrax.exe trace batch `
  --input-dir "." `
  --request "分析每份 Trace，并且需要简短根因" `
  --lang zh
```

`.` 表示当前目录。

程序会把每个真实 Trace 文件的路径通过 `--htrace` 传给独立分析子进程，不会只传提示词。

默认识别常见后缀，例如：

- `*.trace`
- `*.systrace`
- `*.htrace`
- `*.atrace`
- `*.ftrace`
- `*.perfetto-trace`
- `*.perftrace`
- `*.tracebundle.json`

对于 `.txt`、`.log` 或无后缀文件，程序只读取一个有限大小的文件开头，并检查是否包含 `sched_switch`、`sched_wakeup`、Binder 等真实 Trace 标记。普通日志不会被随便当成 Trace。

需要扫描子目录时增加：

```powershell
--recursive
```

## 10. 批量输出目录里有什么

```text
输出目录
├── findings
│   └── 每份 Trace 的结构化 TraceFinding JSON
├── reports
│   └── 每份 Trace 的完整长答案
├── logs
│   └── 每份 Trace 的诊断和错误日志
├── clusters.json
│   └── 机器可读的聚类结果
└── report.md
    └── 人可以直接阅读的聚类报告
```

`reports` 和 `logs` 分开保存，因此诊断日志不会混入长答案。

## 11. 聚类怎样工作

每份 Trace 先独立生成结构化 Finding。

程序再使用稳定字段生成根因指纹，包括：

- 根因 Token；
- 线程角色；
- 上游角色；
- 因果形态；
- 阶段；
- 规范化事件；
- 规范化调用位置。

PID、TID、地址和具体耗时等容易变化的实例信息不会单独决定聚类。

指纹相同的主因会进入同一组。证据不足的 Trace 会进入未确定列表，不会被强行塞进某个组。

单个 Trace 不需要聚类，也能显示简短根因。聚类只负责整理多份 Trace。

## 12. `providers.yaml.example` 现在负责什么

数据库根因模板已经撤回。

`providers.yaml.example` 现在仍然只保存模型 Provider 的示例配置，例如：

- 模型服务地址；
- API Key；
- 模型名称；
- 请求路由和超时等模型设置。

简短根因的 11 类规则直接由程序代码维护，不连接 PostgreSQL，也不需要数据库地址、端口、账号或密码。

## 13. 最核心的思想

一句话概括：

> 原来的模型继续生成完整长答案；程序另外从真实 Trace 的结构化证据中选出主因，按固定格式生成可选 JSON，再用同一份结构化结论完成多 Trace 聚类。

这样同时保证：

- 真实读取 Trace；
- 简短根因格式统一；
- JSON 方便程序继续使用；
- 不需要数据库；
- 不影响原来的长答案；
- 只有用户需要时才显示简短根因。

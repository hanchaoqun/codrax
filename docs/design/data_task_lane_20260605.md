# Data Task Lane Plan (2026-06-05)

## Problem

Recent customer data-cleaning runs exposed a systemic gap: structured and
semi-structured data tasks are currently forced through the source-analysis
pipeline or through generic computer operations. That causes several failures:

- Source-analysis gates treat CSV/manifests/attachments as implementation
  anchors and may reject valid data tasks for lacking source-symbol coherence.
- Read-mode `exec_command` correctly blocks arbitrary Python, so deterministic
  calculations fall back to model hand arithmetic.
- `member_set` aggregate facts are count-oriented; using them to carry numeric
  totals causes value normalization and metric drift.
- Final answers are generated by a prose finalizer, so strict user output
  formats such as JSON-only, CSV-only, single-line strings, or Markdown tables
  are not reliably enforced.

This is not a procurement-specific issue. It is a missing first-class lane for
read-only data processing.

## Red Lines

- Do not route data tasks through source-code evidence gates.
- Do not weaken read-mode `exec_command` for source/log/trace analysis.
- Do not classify by Go keyword matching or by parsing model prose.
- Do not make data task routing affect code, log, trace, MCP, operation, or
  write-mode stability.
- Do not let model hand-calculation replace deterministic computation.
- Do not hard-code a single output format; all strict output shapes go through a
  typed `OutputContract`.

## Selected Architecture

Add a separate typed REPL/CLI route: `route=data`.

The route is selected only by the existing structured turn-policy classifier.
It is not part of the source-analysis pipeline and is not ordinary command
operation. The classifier emits typed data fields:

- `needs_data_access`
- `data_task_kind`

The data lane uses a dedicated planner and a deterministic read-only runner:

1. Discover a compact set of candidate local data files without building
   `repo_map`.
2. Ask the data planner for a typed plan:
   - input paths
   - output contract
   - bounded Python calculation body
3. Copy selected input files into a temporary work directory.
4. Execute the calculation body inside a restricted helper that provides data
   APIs such as `csv_rows`, `tsv_rows`, `json_load`, `jsonl_rows`, `read_text`,
   `parse_money`, and `emit`.
5. Parse the emitted JSON result and validate it against `OutputContract`.
6. Render only the final requested data answer, plus a compact audit summary
   when explanations are allowed.

The helper intentionally does not expose `open`, `__import__`, shell execution,
or repository write access. It is not a perfect OS sandbox, but it is much
safer than enabling arbitrary read-mode shell/Python in the existing analysis
pipeline, and it keeps all repo writes out of scope by copying inputs to a
temporary workspace.

## Output Contract

Supported initial output formats:

- `plain_single_line`
- `csv_line`
- `json_only`
- `markdown_table`
- `markdown`
- `file_path`
- `freeform`

`explanation_allowed=false` means the user-facing answer must be exactly the
computed `answer` string. This is the generic mechanism for “only output X”
requirements.

## Non-Goals

- No XLSX writer/editor in this batch. Existing spreadsheet/document plugins
  remain separate.
- No source-code citations for data rows.
- No automatic data lane fallback when classifier fails; fail-safe remains the
  existing source-analysis pipeline.
- No procurement-specific business logic.

## Post-Integration Risk Audit

- **Risk: route=data overfits strict output wording.** A request may ask for
  `JSON-only`, `CSV-only`, or a table while still being a source-code,
  trace/log, MCP, or previous-answer task. Mitigation: classifier prompt and
  schema now state that strict output format alone is not sufficient for
  `route=data`; the data lane requires local data materials plus a data
  calculation/cleaning/aggregation/transform goal. A guard test preserves
  source `JSON-only` requests as `route=repo`.
- **Risk: CLI single-shot pays multiple classifier calls.** Adding a data
  preflight before operation initially meant a non-data request could classify
  once for data and again for operation. Mitigation: CLI single-shot now makes
  one typed route-policy call and lets data/operation/pipeline consume that
  same guarded policy. This keeps source, trace/log, mixed, and operation
  routing stable while avoiding extra LLM/provider cost.
- **Risk: output contract becomes a hard answer gate.** User-requested output
  shape should guide rendering and deterministic repair, not block unrelated
  source/trace/log/write answers. Mitigation: normal pipeline routes carry
  output shape as presentation/output guidance only. Data lane validates its
  deterministic runner output, but contract mismatches are softened into
  normalization plus `contract_warnings`; they do not hard-stop the whole
  answer. Strict-output responses omit warning prose from the user-visible
  payload to avoid violating the requested shape.

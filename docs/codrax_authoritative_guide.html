CODRAX 使用与技术说明

CODRAX —— Code Of Deterministic Reasoning, Anchored eXplanation.

推理确定，解释锚定。每条结论落到代码，每段推理可以复核。

确定性诚实，不是态度，是契约。

这份文档分两部分：前半段教你怎么用——四条上手路径、典型场景、怎么提问； 后半段用大白话讲它内部怎么工作——为什么答案能锚定到代码、为什么它会在证据不足时诚实地停下。 不需要任何前置知识，从上往下读即可。

一句话看懂 CODRAX

CODRAX 是一个代码分析 + 变更提议工具。默认运行在读模式， 围绕可复核证据回答代码行为、崩溃根因、性能卡顿、默认配置、模块职责等问题，全程不碰源文件； 开启写模式后，还能在沙箱工作区（隔离出来的临时改动区，不直接动主仓）里走完整的 计划 → 改动 → 验证 闭环。

可以把它当成什么

  • 一个会读仓库、会追证据、会给引用的高级分析助手。
  • 一个适合新人熟悉系统、线上排障、架构讲解的工程工作台。

不该把它当成什么

  • 不是“模型直连仓库”的聊天壳。
  • 不是靠文风自信来制造正确感的问答器。

一个正确预期

  • 它承诺的不是“永远秒答”，而是“能证实的尽量证实，证不实的明确标边界”。
  • 价值在于更稳地把复杂问题拆清楚。

四种使用形态

形态适合什么
边问边查交互控制台，适合摸清陌生系统、连续追问。
一次分析单次请求 -r "…"，适合脚本和持续集成。
现场输入挂日志或性能文件，先分诊再追代码。
安全改动写模式先在沙箱验证，不直接改主仓。

安装与开始之前

真正开始提问之前，有三件事要先准备好：装好 codrax、配好大模型凭证， 然后进到你要分析的代码仓库里启动它。三步走完，就能问出第一个问题。

第一步 · 装好 codrax

两种方式，任选其一：

方式一：下载发布包（推荐）

到下载页取对应系统的发布包，解压即可。包内含 codrax 可执行文件、两份配置样例和这份手册，开箱即用。

方式二：从源码构建

需要 CGO（tree-sitter 语法解析）。macOS 先 xcode-select --install，Debian / Ubuntu 装 gcc musl-tools。

git clone https://github.com/hanchaoqun/codrax.git
cd codrax && make   # 输出 ./codrax

建议把 codrax 所在目录加进 PATH，这样在任何地方都能直接敲 codrax 启动：

echo 'export PATH="/path/to/codrax:$PATH"' >> ~/.bashrc   # bash
echo 'export PATH="/path/to/codrax:$PATH"' >> ~/.zshrc    # zsh
exec "$SHELL" -l

第二步 · 配置 providers.yaml（连接大模型）

codrax 自己不含大模型，要连一个 OpenAI 兼容的 LLM 服务 —— OpenAI、DeepSeek、Qwen、本地 vLLM / Ollama 都可以。 把配置样例复制成 providers.yaml，放在和 codrax 可执行文件同一个目录下： 

cp providers.yaml.example providers.yaml

最小配置只需要填 4 个字段：

llm:
  default:
    provider: openai                 # 协议名；兼容服务都填 openai
    api_key: "sk-xxx"                 # 你的 API key
    model: "your-model-id"            # 例如 gpt-4o-mini / deepseek-chat
    base_url: "https://api.openai.com/v1"

缺字段会怎样：这 4 个字段缺任何一个，codrax 启动时会直接报错并告诉你缺的是哪个 —— 它不会偷偷连任何公网地址。需要按 agent 分别换模型时，再加 agents: 段即可。

第三步 · 进入你的代码仓库再启动

⚠ 这一点最容易被忽略，但最关键

codrax 把「你启动它时所在的目录」当作要分析的代码仓库。它不会弹窗问你「要分析哪个项目」—— 默认分析的就是当前工作目录（等价 --repo .）。

所以正确用法是：先 cd 进你想分析的项目根目录，再运行 codrax。如果在别的目录启动，它就会去分析那个目录。

cd /path/to/your/project   # ① 先进入你要分析的代码仓库
codrax                     # ② 再启动，它会索引「当前目录」这个仓库

启动后 codrax 会在当前目录建一个 .codrax/ 子目录，存放日志、对话记忆和缓存等运行产物。 读模式下它只读你的源码、从不修改；所有运行产物都集中在这一个隐藏目录里，一条 .gitignore 就能排除。

随后你就进入了交互控制台（REPL）：看到提示符 ❯❯ 之后，直接打字提问、回车即可。 /help 列出全部命令，/exit 退出。下一节会展开讲不同的使用路径。

快速上手：4 条路径

不用一次学全。先挑一条最贴近你当前需求的路径开始，其它三条用到再看。

路径一 · 交互控制台

直接对话式提问，适合陌生仓库摸底、连续追问、边看边缩小范围。控制台会自动保留上下文记忆。

codrax
# 然后直接提问：
订单状态为什么没有更新？
如果继续追查，下一步应该先看哪一层？

路径二 · 单次请求

一条命令、一个答案，适合脚本、持续集成（CI）、批量分析，或只要一个明确结论就结束的场景。

codrax -r "退款单为什么会被重复创建？
如果证据不足请明确说明。"

路径三 · 日志 / 性能现场分诊

把崩溃日志或性能 trace 作为附件喂进来。日志会先走日志分诊，性能现场会先走性能分诊—— 这里的“分诊”就是先把现场信息分类整理，再决定从哪里查起。 

codrax --log crash.log -r "解释最可能根因"
codrax --htrace perf.trace -r "为什么这个页面会掉帧？"

路径四 · 写模式闭环

已经明确要改什么时用。进入改动 / 验证阶段时，所有写入都只发生在沙箱工作区。

codrax --mode=plan -r "修复回调幂等问题并补测试" --plan-out plan.json

建议：把交互控制台当成探索工作台，把单次请求 -r 当成稳定分析入口。 多仓父目录下可用 --multi-repo=true 自动发现子仓，再用 --focus 固定本轮目标仓。

典型使用场景

下面五个场景覆盖了大多数日常用法。例子里的文件名、函数名都是占位符，换成你项目里的实际名字即可。

理解代码与机制追问

场景 A · 快速读懂陌生模块

codrax
这个订单创建流程分几层？
要理解超时控制，先看哪几个文件？

先搭骨架，再钻细节。得到的是有证据支撑的分层解释，而不是一段没有重点的概述。

场景 B · 解释一个具体行为

codrax -r "为什么未登录用户也能访问
这个接口？请给关键条件、调用位置、
仍未证实的部分。"

高价值用法。系统会围绕条件、调用路径和边界组织答案，而不只是复述函数名。

线上现场排障

场景 C · 崩溃 / 异常

codrax --log crash.log -r "结合
日志解释最可能根因"

系统会先识别空指针、越界、死锁、权限、配置等常见故障类型，再给出候选根因、已排除项和仍缺证据。

场景 D · 性能 / 掉帧

codrax --atrace perf.atrace -r
"卡顿最可能出在哪个阶段？"

支持 HiTrace、atrace、systrace、perfetto 等常见文本格式，自动抽出关键帧、掉帧、阻塞和启动信号。

场景 E · 多文件联合

codrax --log a.log --log b.log
-r "对比两次崩溃差异"

支持多文件追加，也支持日志 + 性能现场两路信息同时挂载。

写模式起手式：/mode plan 先生成计划和差异预览 → /approve 后才进入改动 + 验证 → 失败可回灌计划器，成功可保留沙箱工作区继续复核。

怎么提问效果最好

同样一个工具，问法不同，效果差别很大。这一节是“使用效果的分水岭”。

更推荐这样提问

  • 是什么 + 由什么决定 + 失败边界在哪
  • 请区分显式定义、推断补全和证据不足
默认超时时间到底是多少？
如果找不到，请明确说明是推断，
还是当前证据不足。

更推荐这样阅读答案

  • 先看它引用了什么文件，再看它怎么总结。
  • 分清哪些是已证实的，哪些只是尽力推断的。
启动提示 → 任务列表 / 处理中
→ 系统决策推演 → 最终答案 + 引用

不要只问“这是什么”，尽量问“它怎么工作、由什么决定、哪些情况会让它失效”。 如果是在多仓父目录提问，顺手说明目标仓，或先用 /repos 看清子仓列表。

为什么不直接把问题丢给大模型

在 CODRAX 里，模型没有“看完整个仓库后自由发挥”的权力。分析阶段只能先做轻量预扫， 确认仓库里有没有用户提到的对象；多仓时还要先确定本轮该看哪些子仓。随后它必须把问题写成结构化任务单—— 写不出来就停下。后面的调查顺序、停止条件、引用合法性和答案放行，都由确定性代码接管。

用户请求→ 轻量预扫→ 分析清单→ 调查→ 提炼→ 验收→ 带引用的答案

模型被限制在很窄的位置

  • 前置分析只看仓库结构、搜索结果和文件列表，先确认“仓里有没有这个对象”。
  • 这一阶段不能读文件正文，也不能直接写最终答案。
  • 没有产出结构化任务单，系统会报错重试。

真正掌舵的是确定性管线

  • 任务单会继续被编成调查路线、证据清单、候选假设和答案验收规则。
  • 这些结构来自固定代码流程；同样的问题再跑一遍，看的仍是同一套停机条件和校验闸门。
  • 多仓时会明确本轮参与的子仓，没参与的不会被悄悄当证据。

这就是它的核心价值

  • 能回答时，会给结论、证据来源和边界说明。
  • 证据不够时，不会用态度把不确定包装成确定。
  • “会停下”本身就是能力，不是模型刚好谦虚。

技术一把一句话编译成调查任务单

用户的一句话不会被直接拿去查仓库。系统先把它拆成几个明确问题，再压成一份结构化任务单—— 后面每个阶段面对的都是这张任务单，不是用户原句。

同一句话，先拆成 6 个问题

“支付回调偶发失败，为什么订单
没有变成已支付？”
  • 这是查根因、查默认值，还是准备直接改代码？
  • 主体是谁：支付回调、订单状态、幂等控制，还是事务提交？
  • 真正要解释的，是“为什么没更新”、哪条条件链生效，还是某个配置值？
  • 第一批先看哪里：入口文件、状态流转、日志、测试，还是事务落库点？
  • 哪几条假设必须同时摆出来比较？
  • 查到什么程度才算够，答案要按什么形态交付？

这 6 个问题，压成 5 类结构

  1. 01
    问题归类

    定清楚“这题是什么题、主体是谁、最后想交什么”——这里被定成“根因排查”。

  2. 02
    调查路线

    排出调查顺序：先查回调入口，再查去重逻辑，再查事务与状态落库。

  3. 03
    证据清单

    列出优先材料：入口处理代码、状态机、日志、测试和相关配置。

  4. 04
    收尾标准

    写清“查到什么程度才算够”，例如关键假设都被证实或排除。

  5. 05
    答案规则

    规定最后必须怎么说，例如一定要区分已证实、已排除、仍缺证据。

这张任务单不是一条提示词，而是一次确定性编译

一旦前置分析交出结构化任务单，后面十几步就交给固定代码管线：纠偏、统一名字、排出调查路线、补风险和假设，最后过质量门。 模型交的是原料，不是成品。

  1. 1
    先纠偏

    分清题型和交付形态（问根因、问精确值，还是一个诚实的“暂时没找到”），再补上调查方向：重点查调用链、注册点、返回值，还是条件分支。

  2. 2
    把名字统一

    把“支付回调”“回调通知”“pay callback”这类别名并到同一对象上，再确认哪些词是代码对象、哪些只是业务口语。后面所有阶段围绕同一套名字工作。

  3. 3
    排出调查路线

    排出调查顺序，并列出材料单和收尾条件：该读哪些文件、日志、测试，查到什么程度才允许结束。

  4. 4
    补风险与假设

    六个风险维度都会打分：安全、数据一致性、兼容性、性能、运维、合规；并给每条假设补上成立条件和打掉条件。

  5. 5
    过质量门并收尾

    字段不完整、调查路线不合法、假设没人负责验证、结构自相矛盾，都会被直接打回重做。日志里出现但仓库对不上的路径、符号，会被当成未验证线索隔离。

通俗理解：内部把它叫 AnalysisIR，你可以理解成“分析任务单”—— 把一句自然语言问题，翻译成一份可执行、可停机、可验收的调查协议；多仓时还会写明本轮锁定哪个子仓。

技术二假设驱动规划，先立可证伪假说

CODRAX 不是“先猜一个答案再找理由”，而是先并列摆出几条可能，再让每条都带上验证条件和淘汰条件， 按证据顺序逐条排查。

假设按题型生长，不是自由发挥

  • 根因题——长出“症状由哪个模块或依赖链导致”的假设。
  • 配置题——长出“默认值到覆盖值是不是只有一条解析链”的假设。
  • 枚举题——长出“答案是不是有限集合”的假设。
  • 双主体关系题——长出“这两个对象有没有直接关系”的假设。

每条假设带两把尺子

  • 成立条件——例如关键符号必须出现、证据至少 2 条。
  • 打掉条件——例如没有调用点、解析链不止一条、相关证据为 0。
  • 状态只有 4 种：未定、成立、被推翻、证据不足。
  • 优先级再按 35 / 30 / 20 / 15 打分，决定先排哪条。

拿支付回调的例子，会长出三条假设

假设 A · 验签没过

支付平台明明回调了，但服务端日志连续出现“签名非法”。系统先看验签分支、错误码和失败日志；如果同批回调都能通过验签，这条会被压低甚至推翻。

假设 B · 幂等吞单

“幂等”白话说就是：同一笔回调来 1 次和来 2 次结果应该一样。平台重试回调，系统却把第二次当“重复请求”跳过——钱到了、订单没改。这时重点看去重键、锁和幂等记录。

假设 C · 提交链断裂

业务代码已经走到“准备把订单改成已支付”，但后面的事务提交、状态落库或异常回滚出了问题，数据库里还是未支付。系统顺着提交点和落库点核对这条链。

通俗理解：内部简称 HDP（假设驱动规划）。关键不是“先猜”， 而是“先并列摆出几条可能，再让每条都带上验证条件和淘汰条件”。

技术三把调查、提炼、成稿拆开

先调查，后提炼，再成稿。中间每一步都换人、换权限，只允许传固定字段的结构化表单—— 不允许把“我大概觉得”直接带进下一段。

第一段 · 只调查

  • 负责读代码、跑搜索、挂日志和性能现场。
  • 产出的是“证据条目、已读文件、工具结果”这类事实，不是结论段落。
  • 即使已经猜到答案，这一段也不能直接下结论。

第二段 · 只提炼

  • 只能看前一段冻结下来的证据快照。
  • 产出“答案骨架 + 假设判决”，例如“幂等吞单更像成立，验签失败基本排除”。
  • 这一段没有文件权限，不能临时回头补读。

第三段 · 只成稿

  • 把骨架渲染成最终文档，整理成“已证实 / 已排除 / 仍缺证据”的结构。
  • 随后立刻做引用与合约的预演验收。
  • 过不了只能退回，不能边写边补调查。

为什么这样更诚实：如果调查段没读到某个关键文件，后两段就没有权限回头补读， 更没有权限把它“脑补”进最终答案。写模式里的 plan → apply → verify 也是同一套思想：理解、改动、验证彼此隔离。

技术四证据落点校验

结论必须落到真实代码和现场上。每一条引用，系统都要确认它真的指向了仓库里存在的那一处。

先做两层硬校验

  • 第一层：引用行和前后几行里，那个符号或关键词是否真的出现过。
  • 第二层：结构身份对不对——这是定义、调用、导入，还是条件分支。
  • 两层都过，才算“这句话真的落到了代码上”。

行号漂了也不会乱放行

  • 先在同文件里按完整名称找（代码改动后函数整体下移很常见）。
  • 再按附近片段在一小段范围里做模糊修复。
  • 还会看同包同名符号、最近调用点和最近条件点。
  • 日志 / 性能现场里提到、但仓库对不上的路径或函数，只能当线索，不能当最终引用。

举个例子：系统说“订单状态是在 applyPayment() 里被写成已支付的”， 它不只要给出文件和行号，还要证明附近真的出现过这个函数、那里确实是状态写入； 如果这个函数名只出现在日志里、仓库查不到，就必须标成未证实线索。

通俗理解：这一步内部叫 Grounding（落点校验）—— 判断一句话能不能准确落到真实代码的某一处。

技术五引用闭环

只能引用自己真正读过的内容。“扫到”不等于“读到”——系统会为这两件事单独记账。

候选集合

只是搜出来、扫出来、看上去可能相关的文件，比如一下子搜出 20 个带 payment 的文件。

已读集合

系统真的打开过正文、手里确实有内容的文件，比如只认真读了其中 3 个关键文件。

待读集合

系统判断关键、但当前还没真正打开的文件。

最终允许引用的清单只能来自“已读集合”，不能来自“我记得那里好像有”。

系统会盯住“有没有实质进展”

  • 每一轮都比对：已读文件、证据条目、引用位置有没有增加，而不是只看模型又说了多少话。
  • 如果有待读文件一直没被读，系统最多每轮代你补读 3 个关键文件。
  • 已被判定为不可信的日志路径或符号，后面读文件、搜索和最终引用都会避开。
  • 连续 2 轮没进展，强制扩大搜索；连续 3 轮还没进展，结束调查并降级输出。

调查结束前还有一道预演验收：当调查代理想宣告“我查完了”， 系统会先模拟最终答案能不能过关——有没有还没读的关键文件、可用引用够不够、列表和数字有没有列全、 说法和题型有没有对上。过不了就继续查。

通俗理解：内部简称 CGEC（引用闭环检查）—— 说法、来源、已读事实、合法引用、最终验收，必须一条链地对上。

技术六可执行合约与停机降级

答案验收不是一个 if，而是一组可机检规则逐条求值。每一种状态都对应固定分支。

系统硬验这 4 类规则

01 题型匹配

这题该回答精确值、步骤、列表，还是机制解释。

02 引用完整

该给文件和行号时，就不能只给一段模糊描述。

03 证据到位

关键假设是否都已裁决，必须满足的证据是否已经齐了。

04 答案完整

数字题要有来源，列表题要列够，调用链要有关键节点，对比题两边证据不能失衡。

符号存在、证据数量、引用数量、假设状态、目标唯一性和答案覆盖度都会算进去。 最能体现价值的是精确题（必须找出唯一解析链才敢给精确值）和 空结果题（查过该查的路径后，允许给一个诚实的空结果）。

验收后的四种出口

绿灯证据与格式都过关

允许输出精确答案并附合法引用。例如“默认超时是 30 秒，定义在某文件某行”。

黄灯只有方向，没有精确落点

只能给方向感，不能包装成精确结果。例如只能说“更像幂等控制吞单”。

红灯关键目标缺失

触发显式失败：明确停下并说明原因，绝不把“不知道”伪装成“知道”。

什么时候继续查，什么时候降级

继续查 / 系统代你补读

  • 还有关键文件没读、可用引用不够、说法和题型对不上——“调查完成”会被降级。
  • 连续 2 轮没进展又存在明确待读文件时，框架每轮最多代你补读 3 个关键文件，只补漏。

降级收尾 / 明确失败

  • 连续 3 轮仍无新增已读事实，就结束调查、输出“尽力结论”，但必须讲清不确定和缺证据。
  • 合约还是过不了、精确目标一直找不到，直接说明失败原因，不拿相似函数冒充结果。

通俗理解：内部把这组规则叫 Criterion（答案验收规则）。 这就是“确定性诚实”——不是模型愿不愿意谦虚，而是每一种状态都对应固定分支。

写模式沙箱：能改，但不莽撞

写模式不是“放开让模型改文件”，而是把改动拆成 计划 → 改动 → 验证 三段，每段权限都不同。 所有写入都只发生在独立沙箱工作区——可以理解成主仓旁边一块临时隔离施工区，里面怎么改都不会碰到主仓当前版本。

计划阶段 · 先把改什么说清楚

  • 生成一份改动计划，列出目标文件、改动类型、依赖顺序和验证要求。
  • 用户先看计划和差异预览，再决定要不要批准。
  • 没有批准，后面的写入阶段根本不会开始。

执行阶段 · 只能按计划落地

  • 改动范围保护：计划没写的模块，执行时不能突然去改。
  • 改动顺序保护：有依赖关系的改动必须按顺序落地。
  • 跨仓写入保护：一次写模式只能改一个子仓。

验证阶段像工程流水线，不是聊天补救：会跑静态检查、预编译检查和测试工具探测； run_tests 自动探测 12 类常见测试工具。验证失败时，系统把失败摘要、测试结果和嫌疑文件回灌给计划阶段， 重做下一版计划。成功后还可以保留沙箱工作区继续复核。

走一个真实问题

把前面所有机制串起来看一遍，核心价值才看得清。

问题：支付回调偶发失败，日志显示回调已到达，
      但订单状态没有变成“已支付”。
分析清单→ 假设排序→ 落点与线索校验→ 引用对账→ 结果验收→ 交付诊断

1 · 先把“查什么”定下来

系统把问题定成根因排查，优先看回调入口、幂等控制、事务提交和状态落库；多仓时先锁定相关子仓。

2 · 让几条假设彼此竞争

可能是验签失败、幂等吞单、也可能是事务回滚。谁先查不看感觉；日志里对不上的路径会先隔离。

3 · 交付边界清楚的结论

不会只说“我猜是幂等问题”，而是“验签问题已基本排除；幂等路径最可疑；事务回滚仍缺直接证据”。

CODRAX 的核心价值，不是比别人更会说，而是把“已证实、已排除、仍缺证据”三件事拆开说清楚。

全链路总览

把它看成一台“只允许有限分支”的调查状态机：模型负责读现场和交阶段结果； 系统负责决定证据是否成立、流程是否继续、答案是否放行。

用户输入 模型参与 系统硬控 固定出口
用户问题 / 附件→ 分诊与分类→ 生成分析任务单→ 调查 → 提炼 → 成稿→ 验收与出口

模型参与的地方

把问题和现场读成结构化输入，并在分类、调查、提炼、成稿这些节点上给出下一步动作和答案草稿。

系统硬控的地方

把问题编成调查路线、证据清单和答案要求；多仓时先确定本轮子仓；不可信现场线索会被隔离，再由引用对账和答案验收决定出口。

写模式也受同一边界

仍然要求先出计划、再落改动、最后验证；写入只发生在沙箱工作区，同时限制可改范围、改动顺序和测试结果。

“解释锚定”就是关键结论必须落回真实文件和行号；“推理确定”就是系统只允许有限状态迁移。 它靠的不是模型“态度诚实”，而是系统把可走分支、可用证据和可放行答案都限制住。

CODRAX 不是让模型替你“装懂代码”，
而是让系统在可验证契约里，
把分析做实、把引用做牢、把不确定说清。

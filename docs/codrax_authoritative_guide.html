一句话定义 CODRAX

CODRAX 是一个代码分析 + 变更提议工具。默认运行在读模式，围绕可复核证据回答代码行为、panic 根因、性能卡顿、默认配置、模块职责等问题；开启写模式后，还可以在沙箱 Git Worktree 中走完整的 plan → apply → verify 闭环。

你可以把它当成什么

  • 一个会读仓库、会追证据、会给引用的高级分析助手。
  • 一个既适合 onboarding / 排障 / 架构讲解，也支持审批后进入写模式闭环验证的工程工作台。

你不该把它当成什么

  • 不是“模型直连仓库”的聊天壳。
  • 不是靠文风自信来制造正确感的问答器。

一个正确预期

  • 它承诺的不是“永远秒答”，而是“能证实的尽量证实，证不实的明确标边界”。
  • 价值在于更稳地把复杂问题拆清楚。

Quick Start
03 / 16

最快上手的 4 条路径

方式一：REPL 交互

codrax explorer 的 ShouldStop 是怎么决定的？ AnalysisIR 哪些字段会影响后续调查？

适合陌生仓库摸底、连续追问、边看边缩小范围。自动保留上下文记忆。

方式二：单次请求

codrax -r "explorer 默认使用哪个 skill？ 如果证据不足请明确说明。"

适合脚本、CI、批量分析，或者只要一个明确答案就结束的场景。

方式三：日志 / Trace 分诊

codrax --log crash.log -r "解释最可能根因" codrax --htrace perf.trace -r "为什么这里会掉帧？"

日志先走 log_triage，性能 trace 先走 perf_triage；两者也可以一起挂载。

方式四：写模式闭环

codrax --mode=plan -r "修复 /worktree 参数处理并补测试" --plan-out plan.json

适合已经明确要改什么。进入 apply / verify 时，写入都只发生沙箱 worktree。

把 REPL 当成探索工作台，把单次请求 (`-r`) 当成稳定分析 API；把 `--log/--htrace` 当成现场输入；把写模式看成“先计划、再审批、最后沙箱验证”的工程闭环。

用户场景一：理解代码与机制追问

A：新同事快速读懂陌生模块

codrax analyze 阶段会产出什么？ AnalysisIR 哪些字段约束了后续步骤？ 如果我要理解 Grounding，先看哪几个文件？

先搭骨架，再钻细节。得到的是有证据支撑的分层解释，而非项目大杂烩。

B：解释一个具体行为

codrax -r "ShouldStop 是怎么决定的？ 请给关键条件、调用位置、仍未证实的部分。"

这是高价值用法。系统会围绕条件、调用路径和边界组织答案，而不只是复述函数名。

为何适合 CODRAX

因为它要读代码并说明“逻辑决定条件”，天然需要物理证据支撑。

推荐追问方式

“这是直接条件还是旁路？”“哪个分支会短路它？”

产出价值

带具体 `file:line` 引用的答案，极适合做 Code Review 或架构文档底稿。

用户场景二：日志、性能 trace 与写模式闭环

C：Panic / Exception 排障

codrax --log crash.log -r "结合日志解释最可能根因，并指出仍缺什么证据"

系统会给出候选根因、已排除项和仍缺失的证据，不只是“猜一个答案”。

D：性能 Trace / 掉帧分诊

codrax --atrace perf.atrace -r "where is the jank coming from?"

支持 HiTrace / atrace / systrace / perfetto 文本，自动抽出 Frames / Janks / Stalls / Startup。

E：多文件 / 双通道联合排障

codrax --log a.log --log b.log -r "对比两次崩溃差异" codrax --log hilog.txt --htrace jank.trace -r "卡顿后 crash 的根因"

支持多文件 append，也支持日志 + trace 两路现场同时挂载。

写模式起手式

  • /mode plan 先生成计划和 diff 预览。
  • /approve 后才进入 apply + verify。
  • 失败可回灌 planner，成功可保留 worktree 继续 review。

REPL 常用控制

/log/htrace/mode/plan/approve/worktree

前两个挂现场，后四个管计划、审批和 worktree 生命周期。

Part II / Architecture
07 / 16

为什么不直接“把问题丢给大模型”？

在 CODRAX 中，大模型（LLM）被物理**剥夺了直接拼凑最终答案的权力**。它仅负责两件事：意图分类，以及在 ReAct 循环里调用受限工具。决定分析轨迹和最终质量的，是 21 个纯 Go 编写的确定性代码包；日志与性能 trace 会先各自走条件前置分诊，再交给 analyzer 消化。

用户请求
→
analyze
→
explore
→
extract
→
finalize
→
带引用的答案

两条主链 + 两条前置

读模式走 analyze → explore → extract → finalize；写模式在 analyze 后分流到 plan → apply → verify；--log 与 --htrace/--atrace 则分别触发 log_triage / perf_triage。

传递强类型结构

层间传递的是 IR 和任务图，拒绝非结构化文本乱飞。

可停、可失败

宁可因为证据不足而报错，也绝不为了“有问必答”去捏造事实。

Semantic → IR
08 / 16

技术一：语义到 IR，把一句话编译成分析协议

避免“望文生义”

“explorer 的 ShouldStop 是怎么决定的？”
  • 这不是简单检索题，而是机制解释题。
  • 系统必须先识别：这是在问条件、停止边界和调用路径。
  • 如果按“找符号定义”去盲搜，整条分析链都会错位。

这份 AnalysisIR v6 的核心层次

  • RequestModel：意图、谓词、主体、动作轴、风险。
  • TaskGraph：节点、依赖、验证回路。
  • EvidencePlan + AnswerContract：调查约束、停机条件、答案形态。
  • HypothesisSet + QualityGate：待证伪假设、质量闸门、是否允许开跑。

沿着这个例子，IR 实际拆出了这些东西

  • 意图：解释机制。
  • 主体：ShouldStop。
  • 谓词：条件、边界、调用链。
  • 动作轴：condition + call。
  • 子话题：停止条件 / 预算 / 证据完备度。
  • 优先文件：写入 RequiredFiles。
  • 答案主体：ShouldStop 的判停机制。
  • 停止条件：facts enough / hypotheses decided。
  • 图示提示：要不要画判停链路。
  • 质量门：coverage、假设绑定、criterion 可求值。
后续阶段拿到的已不是原句，而是一套可执行协议。它会继续经过 normalize → compile → risk → HDP → binder → reconcile → gate。
HDP
09 / 16

技术二：HDP 假设驱动规划，先立可证伪的假说

实战切入：拒绝思维惰性

“结合 panic 解释触发链路”
  • 大模型最容易“看哪个顺眼就认哪个”。
  • HDP 强制先生成多条可证伪假设。
  • 自动进行 6 维风险矩阵评估（安全性、数据完整性等），决定调查优先级。

Counterfactual 反事实推理

对于高风险场景（如鉴权、路由越权），HDP 会自动触发反事实路径，强迫系统思考：“如果不是这样会怎样？” 彻底遏制 LLM 的盲目自信。

排序也不是拍脑袋，而是用确定性权重计算：IntentMatch 0.35 + RiskElevation 0.30 + TermCardinality 0.20 + AmbiguityResolution 0.15。

假设 A：空值穿透

  • 需证据：上游传 nil
  • 证伪：内部有 guard

假设 B：恢复失败

  • 需证据：绕过 recover
  • 证伪：链路被提前拦截

假设 C：缺省降级

  • 需证据：走危险 fallback
  • 证伪：默认配置已补全
Turn A / Turn B
10 / 16

技术三：读模式中的 Turn A/B，调查与总结的物理隔离

物理上切断“边查边编”的可能，确保**调查**与**总结**相互独立。

Turn A：Explorer (只调查)

  • 拿着 analyzer、log_triage、perf_triage 给出的线索，再去读真实源码收集证据快照。
  • 绝对禁令：被物理剥夺了直接输出答案的权限，防止边造假边写。

Turn B：Extractor (只总结)

  • 只能看到 Turn A 冻结的 TurnAArtifacts 证据快照。
  • 绝对禁令：被物理剥夺所有文件 I/O 权限。

隔离效果验证

如果 Turn A 漏查了某个关键文件，Turn B 绝对无法凭空捏造该文件的内容。即使前置 triage 给了很多线索，Turn B 也只能消费 Turn A 真正落盘的证据。它只能受限于 cardinality validator，被迫向用户承认“找不到”或“证据不足”。写模式则对应 planner / coder / verifier 的分工隔离，各自也只拿到自己被允许的工具边界。

Grounding
11 / 16

技术四：物理级证据锚定 (Grounding)

不仅是“看过”，必须能“指认”

如果系统给出结论，它必须能物理证明：这个结论到底锚在代码的哪个文件、哪一行。这分为证据落地和引用校验两层。

弹性挽救机制 (R1-R5)

如果因版本变更导致行号漂移，系统不直接报错，而是执行同名、片段模糊搜索、最近调用点等 5 级挽救，全部失败才坚决丢弃该引用。

T1 校验：字面量重叠 (Line Text)

直接验证读取的文件原文，要求答案的 Token 与源码真实行的邻域 (±1行) 存在物理级的字符重叠，否则判定无效。

T2 校验：符号表匹配 (Symbol Table)

基于 AST（抽象语法树）解析，验证该引用确实落在定义的函数、类型或方法的逻辑作用域内部。

CGEC
12 / 16

技术五：CGEC 引用闭环契约，最严苛的诚实守则

权限世界的严格划分

  • ScannedSet：仅仅是通过文件树/Grep扫描到的候选范围。
  • ReadSet：模型真实调工具读取过正文的集合。

扫描看到名字不等于读到了事实。只有进入 ReadSet 的代码，才允许被写进答案。

四大强制防线 (I1 - I4)

  • I1 真实原则：所有表面引用的 file:line 必须 ⊆ ReadSet。
  • I2 Dry-run 预检：生成答案前做模拟渲染，违规引用直接拦截并触发 RepairReadFile。
  • I4 破局代读：推理卡死时触发 Lazy Auto-Read，框架强行代读文件打破认知瓶颈。
闭环意味着：提出说法 → 找到来源 → 来源确实被读过 → 引用 Token 合法 → 契约验收通过。少任何一环，系统都将被强制拦截。
Criterion
13 / 16

技术六：Criterion 可执行合约

去除主观的“裁判”

任务是否完成，不是靠大模型自己回复 "I have finished"，而是交由系统底层的 19 种读模式 Criterion + 4 种写模式 Criterion做纯逻辑和数学求值。

特例彰显诚实：统计计数题

问“仓库有多少处实现接口？” 答案是统计值。CODRAX 识别为 measurement-scalar 后，承认结果源自聚合，绝不伪造某行假引用去伪装精确。

同样地，问“explorer 默认 skill 是什么？”时，若 ExactResolution 没闭环，系统必须说“还不能精确确认”，不能拿附近配置项充当精确默认值。

找到显式证据

指标亮绿灯，允许输出答案并携带合法锚点。

只看到相邻近似

指标阻断，严禁把“附近看起来像”包装成精确结果。

未知类型

触发 Fail-loud，显式抛出警告让信任降级，绝不默默骗人。

Write Mode Sandbox
14 / 16

延伸：写模式的物理沙箱与 W1/W1b 写闭包

写模式走 plan → apply → verify，但所有写入都只发生在独立 Git Worktree，主仓 HEAD 不会被自动改写。

REPL 演示流

/mode plan /plan show /approve

先看 plan 和 diff，再决定是否 apply；成功后可保留 worktree 继续 review。

CLI 演示流

codrax --mode=plan -r "修复 bug 并补测试" --plan-out plan.json codrax --mode=apply --plan-file plan.json --auto-apply codrax --mode=verify --plan-file plan.json

适合脚本和流水线，plan / apply / verify 可串接，runner 会按仓库类型自动探测。

为什么它能写，但仍然安全

  • W1：只能改 plan 里声明过的目标文件。
  • W1b：依赖顺序不能乱，先后关系错了就拒绝。
  • pipeline_write_retry_budget：verify 失败会回灌摘要、失败测试与嫌疑文件。
  • pipeline_baseline_capture_enabled：区分 REGRESSION / PRE-EXISTING，run_tests 自动探测 11 类 runner。

`events.systrace` 是提供给产品的采集输入；`expected.json` 是独立验收依据，不附加给模型。分析仓为 `eval/fixtures/stub_repo`，不让模型靠读取 oracle 回答。

## 用户应表达的内容

用户只需指定数据、关注窗口、分析对象和希望看到的统计维度；100ms 是其选择的观察粒度，不是正确性防护。当前问题为：

> 帮我看看这份 trace 在 2.00～2.25 秒的 IO 活动：RQ、BIO、MMC、F2FS 各有多少次发起和完成，数据量和速率怎样？再给出 RQ 的读写次数占比和数据量占比、请求大小分布，以及每 100ms 的变化。

## 系统默认负责，验收在问题之外

- 自行选用实际附件的原生统计，保留用户窗口和各独立总体，不让查找容差改变统计范围。
- 正确处理单位、事件自己的字节来源、已知零与未知、半开桶边界、零桶和最后短桶；按实际墙钟分母计算速率。用户不必逐项提醒。
- 活动计数不因无法配对/没有完成而漏掉合法发起；跨层和双端不混加，读写占比分母不混入其他操作。
- 所有已交付数值/关系符合 `expected.json` 及原始行。缺测要在必要位置简明披露，不制造精确值或跨层请求身份；活动量本身不授权等待、并发、硬件饱和或响应根因。
- 正确选择或绑定可信结果，不让模型重算被截断的预览；表与说明一致，采用用户能理解的量尺和标签。

验收不要求答案背诵以上清单，也不要求主动逐段解释每一个人工设置的边界。实际数字、表格及必要的限制说明正确即可；未提某条边界规则不等于失败，错误计数或作出无证据断言才是失败。需要逐项说明边界的场景另作为专家定向合同测试，不代替默认易用性评测。
